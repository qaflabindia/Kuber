## Rules

- **Statuses**, in order: `proposed` → `finance-approved` → `implemented` → `verified` → `operationally proven`; also `blocked` and `failed`.
- **verified** needs a passing test (UAT/test ID resolving to a real `it(`/`describe(` title, `tests/<file>.test.ts::<title>`) *and* an evidence artifact with the tested commit. A describe title stands for every test under it; all must pass.
- **operationally proven** needs observed operation or recovery evidence (a drill or a live period), not a test run.
- **implemented** means the code exists but acceptance is partial; the Deferral/expiry column says what is missing.
- **Engineering moves rows only up to `implemented` or `verified`.** `finance-approved`, `operationally proven` and Finance sign-off are decisions of named people.
- **No sign-off by module name.** A requirement is not accepted because "the GL module" or "identity" owns it: the Business owner must be a named person before any row can be finance-approved, operationally proven or signed off. Until then the column reads `Unassigned — <proposed accountable role>` and Finance sign-off reads `Pending`; the check rejects anything else.
- Review reproductions A01–A14 (`review/architecture-review.test.ts`) assert the *defect* and now fail by design; they are cited in the Source column, never as passing evidence. Evidence is the regression tests in `tests/`.
- A green suite does not waive a failed control. Deferrals need an owner and an expiry set by Finance; until then the expiry reads "to be set".
